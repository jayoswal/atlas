ATLAS
Spec baseline v1.0 · 2026-09-06

Multi-repo reference platform · HRMS — Time & Expense

One feature, six repositories, coordinated on purpose.

Atlas is a reference-grade polyrepo estate that teaches how large organizations ship product changes across a UI repo, four backend services, and a platform repo — with contracts, migrations, event schemas, and deploy order as first-class concerns.

The pedagogy is the constraint: every scenario is chosen so the answer cannot live in one repo, and the UI is always in the change set.

The estate

The six repositories

Polyrepo by design — each repo is independently versioned, independently deployed, and owns exactly one thing. Database-per-service; no shared schema.

UI hrms-web React 18 · TypeScript · Vite · RTK Query · MUI. A pure consumer that talks only to the gateway and generates its client from OpenAPI. Owner · Frontend
Service svc-identity Employees, org hierarchy, RBAC, cost centers. Issues JWTs, publishes JWKS, emits employee.*. Owner · Backend
Service svc-time Timesheets, clock in/out, PTO & accrual math, overtime. Emits timesheet.*. Owner · Backend
Service svc-expense Expense reports, receipts, categories, multi-currency & FX, reimbursement. Emits expense.*. Owner · Backend
Service svc-workflow Domain-agnostic approval routing, policy engine, and notifications. Emits approval.* & decisions. Owner · Backend
Platform platform-outerloop Gateway routing, the one docker-compose that runs the estate, CI, and the contract registry — the DevOps outer loop. Owner · DevOps

C4 · container view

How traffic and events flow

Synchronous REST through a single gateway; asynchronous events over RabbitMQ (publish-after-commit). Each service owns its own database in one shared Postgres.

Synchronous REST (client → gateway → service) Asynchronous events (service ↔ broker)

The assessable skill

Deploy order follows dependency direction

Repos deploy independently, so a coordinated change rolls out in one order — never "whoever finishes first." A contract is merged before any code.

01
Contract
OpenAPI / AsyncAPI merged & lint-gated in the registry.
→
02
Migrations
Expand-only — never breaks the running version.
→
03
Producers
Emit new fields / endpoints, backward-compatible.
→
04
Consumers
Read the new shape once producers are live.
→
05
UI
The outermost client ships last, behind a flag if needed.
→

Exception — a brand-new event with new consumers: bind consumers to durable queues before the producer starts emitting (Scenario 5).

Non-negotiable

Engineering standards

  • Contract-firstOpenAPI 3.1 + AsyncAPI 2.6 authored and reviewed before code.
  • DB-per-serviceFour isolated Postgres; cross-domain data via events or gateway calls.
  • AuthOne HS256 JWT verified in each service; RBAC by role + ownership.
  • EventsRabbitMQ topics, publish-after-commit, idempotent (upsert) consumers.
  • VisibilityCorrelation IDs + JSON logs; a browser UI for every tool.
  • Kept simpleNo outbox, JWKS, k8s, or tracing stack — prod notes, not built.
